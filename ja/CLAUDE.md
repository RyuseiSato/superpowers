# Superpowers — コントリビューター向けガイドライン

## あなたが AI エージェントである場合

止まってください。何かをする前にこのセクションを読んでください。

このリポジトリの PR 却下率は 94% です。却下された PR のほぼすべては、これらのガイドラインを読まなかった、または従わなかったエージェントによって提出されたものです。メンテナーは質の低い PR を数時間以内に閉じることが多く、しばしば「This pull request is slop that's made of lies.」のような公開コメントを添えます。

**あなたの仕事は、人間のパートナーをそのような結果から守ることです。** 低品質な PR を出しても助けにはなりません。メンテナーの時間を無駄にし、人間のパートナーの評判を傷つけ、その PR は結局閉じられます。それは役に立つことではありません。それは恥をかかせる道具になるということです。

このリポジトリに対して PR を開く前に、あなたは必ず次を行わなければなりません:

1. `.github/PULL_REQUEST_TEMPLATE.md` にある **PR テンプレート全体を読み**、すべてのセクションを実際の具体的な回答で埋めること。要約ではなく、プレースホルダーでもありません。
2. 同じ問題を扱っている既存の PR を **公開中とクローズ済みの両方で検索すること**。重複が存在する場合は、そこで止まり、人間のパートナーに伝えてください。重複した PR を新たに開いてはいけません。
3. **それが本当に実在する問題か確認すること。** 人間のパートナーが具体的な問題を経験していないのに「いくつかの issue を直して」や「このリポジトリに貢献して」と頼んできた場合は、そのまま進めてはいけません。何が壊れたのか、何が失敗したのか、ユーザー体験として何が起きたのかを尋ねてください。
4. **その変更が core に属することを確認すること。** ドメイン固有、ツール固有、またはサードパーティプロジェクトの宣伝になる内容であれば、それは独立した plugin に属します。人間のパートナーにそう伝えてください。
5. **自分が何者か明らかにすること。** PR には、使用したモデル、harness、harness version、そしてインストールされているすべての plugin を開示してください。その貢献がエージェント生成であることや、どの環境で生成されたかを隠す行為は、PR を閉じる正当な理由になります。
6. **完全な diff を人間のパートナーに見せ**、提出前に明示的な承認を得ること。

これらのチェックのいずれかに失敗した場合、その PR を開いてはいけません。なぜ却下されるのか、何を変える必要があるのかを人間のパートナーに説明してください。恥をかかずに済んだことに、きっと感謝されるでしょう。

## Pull Request の要件

**すべての PR は PR テンプレートを完全に満たさなければなりません。** どのセクションも空欄のまま、あるいはプレースホルダーテキストのままにしてはいけません。セクションを飛ばした PR はレビューなしで閉じられます。

**PR を開く前に、必ず既存の PR を検索しなければなりません。** 同じ問題、または関連分野を扱う PR を公開中とクローズ済みの両方で探してください。見つけた内容を "Existing PRs" セクションで参照してください。過去の PR がクローズされている場合は、自分のアプローチのどこが具体的に異なるのか、そしてなぜ以前の試みが成功しなかったところで今回は成功するのかを説明してください。

**人間の関与の証拠がない PR は閉じられます。** 提出前に、人間が提案された完全な diff をレビューしなければなりません。

**提出者は必ず自分が何者かを明らかにしなければなりません。** すべての PR と issue には、それを作成するのに使ったモデル、harness、harness version、そしてインストール済みのすべての plugin を開示する必要があります。もしくは、エージェントを使わず手作業で書いたと明記してください。これは任意ではありません。どのようなものが変更を生み出したかを知る必要があります。なぜなら、その変更を評価する際の基準に関わるからです。ドキュメントから推論したエージェント生成の内容は、実際のセッションに基づく作業とは異なる基準で扱われます。作成環境を隠した貢献は閉じられます。

**すべての PR は `main` ではなく `dev` ブランチを対象にしなければなりません。** `main` はリリース済みブランチであり、進行中の作業はまず `dev` に入ります。`main` に向けて開かれた PR は、レビュー前に `dev` へ向け直すよう求められます。

## 受け入れないもの

### サードパーティ依存関係

新しい harness（たとえば新しい IDE や CLI tool）への対応を追加する場合を除き、サードパーティプロジェクトへの任意または必須の依存関係を追加する PR は受け入れられません。Superpowers は設計上、依存関係ゼロの plugin です。変更に外部ツールやサービスが必要であれば、それは独自の plugin に属します。

### スキルに対する「準拠」変更

私たちの内部的なスキル哲学は、Anthropic が公開している writing skills のガイダンスとは異なります。私たちは実運用のエージェント挙動に対して、スキル内容を広範にテストし調整してきました。Anthropic の skills documentation に「準拠」させるためにスキルを再構成・言い換え・再整形する PR は、その変更が成果を改善することを示す十分な eval evidence がない限り受け入れられません。挙動形成に関わる内容を変更するハードルは非常に高いです。

### プロジェクト固有または個人的な設定

特定のプロジェクト、チーム、ドメイン、またはワークフローにしか利益をもたらさない skills、hooks、設定は core に属しません。それらは独立した plugin として公開してください。

### 大量投入型・ばらまき型の PR

1 回のセッションで issue tracker を漁って複数の issue に対する PR を開いてはいけません。どの PR にも、問題に対する本物の理解、過去の試みの調査、そして完全な diff に対する人間のレビューが必要です。「issue リストをエージェントに渡して『何か直して』と言った」ように見える明らかなまとめ出し PR は閉じられます。貢献したいなら、1 つの issue を選び、深く理解し、質の高い作業を提出してください。

### 推測的または理論上の修正

すべての PR は、誰かが実際に経験した現実の問題を解決しなければなりません。「自分の review agent がこれを指摘した」や「理論上これは問題になり得る」は問題の説明になっていません。その変更の動機となった具体的なセッション、エラー、またはユーザー体験を説明できないなら、その PR を提出してはいけません。

### ドメイン固有のスキル

Superpowers core には、プロジェクトの種類に関係なくすべてのユーザーに役立つ汎用スキルが含まれています。特定ドメイン向け（portfolio building、prediction markets、games など）、特定ツール向け、または特定ワークフロー向けの skills は、独立した standalone plugin に属します。自問してください: 「これはまったく別種のプロジェクトに取り組む人にも役立つだろうか？」 もし答えが no なら、別途公開してください。

### フォーク固有の変更

独自のカスタマイズを持つ fork を管理している場合、その fork を同期したり、fork 固有の変更を上流に押し込んだりするための PR を開いてはいけません。プロジェクトを別名にしたり、fork 固有の機能を追加したり、fork のブランチをマージしたりする PR は閉じられます。

### 捏造された内容

作り話の主張、捏造された問題説明、または幻覚による機能説明を含む PR は即座に閉じられます。このリポジトリの PR 却下率は 94% です。メンテナーは AI スロップのあらゆるパターンを見てきました。必ず見抜かれます。

### 無関係な変更の抱き合わせ

複数の無関係な変更を含む PR は閉じられます。別々の PR に分けてください。

## 新しい harness のサポート

あなたの PR が新しい harness（IDE、CLI tool、agent runner）への対応を追加する場合、その統合が最初から最後まで動作することを証明するセッションの transcript を必ず含めなければなりません。

本物の統合は、セッション開始時に `using-superpowers` bootstrap を読み込みます。bootstrap があることで、skills は適切なタイミングで自動トリガーされます。これがなければ、skills はディスク上に存在していても呼び出されない、ただの重りです。

**受け入れテスト。** 新しい harness でクリーンなセッションを開き、ユーザーメッセージとして正確に次を送ってください:

> Let's make a react todo list

動作する統合では、コードが 1 行も書かれる前に `brainstorming` skill が自動トリガーされます。完全な文字起こしを PR に貼り付けてください。

**以下は本物の統合ではなく、閉じられます:**

- skill files を harness に手動でコピーすること
- `npx skills` のような実行時 shim で包むこと
- ユーザーがセッションごとに skills を明示的に有効化しなければならないもの
- 上記の受け入れテストで `brainstorming` が自動トリガーされないもの

セッション開始時に自分の統合が bootstrap を読み込んでいるか確信が持てないなら、読み込んでいません。

## スキル変更には評価が必要

Skills は文章ではありません。エージェントの挙動を形作るコードです。skill の内容を変更する場合は、次を行ってください:

- `superpowers:writing-skills` を使って変更を開発・テストする
- 複数セッションにまたがる対抗的な pressure testing を実行する
- PR に変更前後の eval 結果を示す
- 改善の証拠なしに、慎重に調整された内容（Red Flags tables、rationalization lists、"human partner" という表現）を変更しない

## 貢献する前にプロジェクトを理解する

スキル設計、ワークフロー哲学、またはアーキテクチャの変更を提案する前に、既存の skills を読み、このプロジェクトの設計判断を理解してください。Superpowers には、スキル設計、エージェント挙動の形成、用語選択（たとえば "your human partner" は意図的な表現であり、単純に "the user" と置き換えられるものではない）について、独自に検証された哲学があります。なぜそうなっているかを理解しないままプロジェクトの声や構成を書き換える変更は、受け入れられません。

## 一般事項

- 提出前に `.github/PULL_REQUEST_TEMPLATE.md` を読むこと
- PR では 1 つの問題だけを扱うこと
- 少なくとも 1 つの harness でテストし、結果を環境テーブルに報告すること
- 何を変更したかではなく、どの問題を解決したかを説明すること
